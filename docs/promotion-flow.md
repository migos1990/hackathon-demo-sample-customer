# Pre-Prod → Prod Promotion Flow + Partner Distribution

**Status:** design capture, not yet implemented. Ticket template field `terraform_workspace: staging | prod` already exists; promotion GATE mechanics below are not yet wired.

**Law:** BLAST-RADIUS LAW (Law 8). "Prod has its own environment/ref. No migration touches prod without flowing dev → staging → prod with verify gates between each."

**Scope:** captures two linked design directives:
1. Every SCIM-connector ticket must land in pre-prod first, pass gates, then be manually promoted to prod.
2. This same setup is what Okta PS gives to partners to accelerate customer implementations — so the promotion flow doubles as a partner-safety boundary.

---

## 1. Environment topology

Two tenants, two Terraform workspaces, one connector build.

| Layer | Pre-prod | Prod |
|---|---|---|
| Okta tenant | `demo-customer-a-staging.oktapreview.com` | `demo-customer-a-prod.okta.com` (or customer's real prod for non-hackathon use) |
| Target app endpoint | customer's staging SCIM endpoint (or mock) | customer's prod SCIM endpoint |
| Terraform workspace | `staging` | `prod` |
| Deploy ref | feature branch or `main` | tagged release (e.g. `v1.0.0-acme-hr`) |
| Traffic | synthetic fixtures + manual smoke tests | real Okta lifecycle events |
| Rollback | delete tenant assignment; no blast beyond staging | `terraform apply` of prior tagged ref |

The pre-prod tenant is **not** a dry-run. It's a full live SCIM integration against a real Okta tenant — just one whose only assigned users are synthetic test users generated by `scripts/sanitize-payload.ts`.

## 2. Lifecycle of a ticket

```
1. Consultant files Linear ticket from new-scim-connector.md template
        │
        │   terraform_workspace: staging  (REQUIRED default for new tickets)
        ▼
2. Orchestrator pulls ticket; agent generates connector + Terraform config
        │
        ▼
3. CI runs on the generated PR:
        - tsc --noEmit clean
        - vitest (unit + replay-test) green
        - secret scan clean
        - validators green (SCIM compliance, security baseline, TF baseline)
        - TRUTH-LAW + PLAN-LAW gates green
        │
        ▼
4. PR merged to main  →  Terraform apply to staging workspace
        │
        ▼
5. Pre-prod verify gate (post-deploy):
        - `terraform plan` against staging is empty (idempotency check)
        - Okta OIN SPEC Test suite run against the live pre-prod tenant → 12/12 green
        - Runbook smoke test: create 1 synthetic user, PATCH active:false, verify in tenant
        - Zero errors in server logs during the smoke window
        │
        │   ALL GREEN  →  eligible for promotion
        │   ANY RED    →  ticket stays in pre-prod until fixed
        ▼
6. Manual promotion (human approval step):
        - Reviewer tags the release: `git tag -s v<semver>-<customer-slug>`
        - Promotion Manifest generated (see §4 below) and signed (HMAC-SHA256)
        - Promotion PR opens: flip `terraform_workspace: staging → prod` in ticket
          front-matter, pinning the signed manifest in the PR description
        │
        ▼
7. Terraform apply to prod workspace (SAME code, different workspace)
        │
        ▼
8. Prod verify gate:
        - `terraform plan` against prod is empty
        - Runbook smoke test (synthetic user, if customer's compliance allows;
          otherwise skip this step and rely on the pre-prod assertion)
        - Observability: health metric green, error rate = 0 over first 15 minutes
        │
        ▼
9. Ticket closes as "promoted to prod @ <tag>"
```

**The gate is binary and automated where possible.** Steps 5 and 8 are the only places where the pipeline stops. Step 6 is the only place a human decides — and the human's job is to acknowledge the gate passed, not to re-verify.

## 3. What "pre-prod verify gate" actually checks

The pre-prod verify gate (step 5) is the single most important quality bar — it's what separates "code compiles" from "ready for a customer." Each check is a GATE LAW (Law 7) derived from a reviewer-finding category:

| Check | What it catches | Where it runs |
|---|---|---|
| `tsc --noEmit` clean | type regressions | PR CI |
| `vitest run` green | unit + integration + replay-test regressions | PR CI |
| Secret scan clean | accidentally committed tokens | `.githooks/pre-commit` + PR CI |
| Validators green | SCIM schema compliance, security posture, Terraform baseline | PR CI |
| Idempotent TF plan | Terraform drift between code and tenant state | post-deploy to staging |
| OIN SPEC Test 12/12 | Okta-dialect regression (PATCH semantics, filter, error envelope, auth) | post-deploy to staging |
| Smoke test green | end-to-end lifecycle event works | post-deploy to staging |
| Zero log errors in smoke window | silent failure at wire level | post-deploy to staging |

Every failure here becomes a named GATE — the name goes into the runbook's "what this gate catches" section so the next generated connector inherits the protection.

## 4. The Promotion Manifest (signed)

A manifest pinned at promotion time so the thing that got verified in pre-prod is provably the thing deployed to prod. Mirrors the HMAC-signed Plan pattern from the PS Agent spec §6.8 (RFC 8785 canonical JSON, dual-key rotation, consumed-on-first-use).

**Schema (JSON, canonicalized per RFC 8785 before signing):**

```json
{
  "manifest_version": 1,
  "customer_slug": "acme-hr",
  "ticket_id": "LIN-1234",
  "git_commit": "a1979c4...",
  "git_tag": "v1.0.0-acme-hr",
  "preprod_tenant": "demo-customer-a-staging.oktapreview.com",
  "prod_tenant": "demo-customer-a-prod.okta.com",
  "terraform_module_version": "0.3.1",
  "fixtures_hash": "sha256:...",
  "preprod_verify": {
    "ran_at": "2026-05-04T14:00:00Z",
    "tsc_clean": true,
    "vitest_passed": "62/62",
    "oin_spec_tests_passed": "12/12",
    "tf_plan_empty": true,
    "smoke_test_passed": true,
    "log_errors_count": 0
  },
  "approver_github_username": "<reviewer>",
  "approved_at": "<iso-8601>"
}
```

The manifest is signed at approval time (step 6) and verified before Terraform apply to prod (step 7). Signature mismatch = prod deploy refuses.

**Why this matters:** without a signed manifest, "I tested it in staging" is a verbal claim. With one, it's a cryptographic assertion that the exact commit + fixtures + tenant state that passed verify is what's being promoted.

## 5. Rollback

Prod rollback reuses the same flow in reverse — no special path.

```
Incident in prod
    │
    ▼
Tag prior known-good release is identified
    │
    ▼
Revert PR: flip terraform_workspace back; pin prior manifest
    │
    ▼
Terraform apply of prior ref to prod
    │
    ▼
Prod verify gate runs again against the rolled-back state
```

**Non-goal for hackathon:** automated rollback on health-metric regression. That's a Day-11+ item. Hackathon demo shows manual rollback via a revert PR.

## 6. Ticket-template changes needed

The current template (`ticket-templates/new-scim-connector.md:67`) has `terraform_workspace: staging` as default. To support the gate, add:

```yaml
# Promotion (added)
promotion_gate:
  preprod_verified_at: null           # set by verify gate on pass
  preprod_manifest_sha: null          # set at approval time, consumed on prod apply
  approver_github_username: null      # set at approval time
  promoted_to_prod_at: null           # set by prod apply success
```

These fields are `null` on ticket creation and written to by the pipeline, not the human. Promotion PR diff must show the transition `null → <value>` for each — any other state is a tampering signal.

**Schema update:** `ticket-templates/schema.json` gets a new required `promotion_gate` object. Validator rejects tickets missing it, so old tickets need a one-line migration (add the empty object).

## 7. Partner-distribution framing

**The story:** this same harness — ticket template + 14-law gates + signed-promotion flow + OIN-passing skeleton — is what Okta PS hands to partners who implement Okta at customers on PS's behalf.

**Who uses it:**

| Actor | Role | What they get |
|---|---|---|
| Okta PS consultant | Files tickets, reviews generated PRs, approves promotion | Full repo access, both tenants |
| Partner consultant | Files tickets, implements fixes to generated PRs when agent falls short | Fork of the repo scoped to their engagement, pre-prod tenant only; prod promotion requires Okta PS co-sign |
| Customer IT (read-only) | Observes the pipeline so they can trust what ships to their prod tenant | Read access to the PR trail + signed manifests |
| Agent (Claude Agent SDK) | Generates connector code from tickets | Per-ticket scoped token (Auth0 Token Vault), pre-prod write, prod deny |

**Why a partner wants this instead of hand-rolling:**

1. **OIN-passing skeleton out of the box.** Pre-built skeleton at `skeleton/` passes 12/12 OIN SPEC Tests before the partner writes one line. They ship in days, not weeks.
2. **Ticket-driven, not tribal.** The partner's junior consultants file tickets from a template; the template is the contract. Reduces "senior-on-senior" hand-holding.
3. **Tested-before-prod, provably.** Signed Promotion Manifest means the partner can show the customer "this exact thing passed 62 tests + 12 OIN tests + idempotency check before any prod bit moved."
4. **Auditable PR trail.** Every change is a PR. Every deploy cites a manifest. Customer IT can read the repo and reconstruct the history.
5. **Harness is the moat the partner inherits.** 14 laws + Santa Method gates catch the bugs that otherwise ship to customers and become Okta PS escalations.

**Why Okta PS wants partners on this:**

1. **Blast-radius containment.** Partner writes buggy code → pre-prod catches it, not the customer's workforce locked out on Monday morning.
2. **Consistency across partners.** Twelve partners using the same harness produce connectors that look and behave alike — Okta PS oncall can support them uniformly.
3. **Scales PS reach.** A harness that lets partners self-serve 80% of a SCIM build means Okta PS billable hours move from wire-level plumbing to customer-strategic work.
4. **Feedback loop into the harness.** Every partner engagement surfaces new dialect edge cases; those land in `docs/okta-dialect.md` and harden the harness for everyone.

**Security boundary (MUST preserve):**

- Partner forks are scoped to a single customer engagement. Cross-customer access is a refuse.
- Partner credentials (tenant API tokens, Terraform state backend, Auth0 agent tokens) are per-fork, never shared across engagements.
- Prod promotion requires Okta PS co-approval — partner cannot promote to customer prod unilaterally. Mechanism: two-of-two signature on the Promotion Manifest (partner + Okta PS reviewer).
- Customer data never enters any repo. `scripts/sanitize-payload.ts` is the boundary; CI refuses PRs that match real-customer-data patterns (already enforced for hackathon).

**Open items for partner distribution (not blocking hackathon):**

- Onboarding flow: how does a partner get a fork + pre-prod tenant provisioned? Manual for hackathon; automate later.
- Auth isolation: Auth0 tenant per partner? Per engagement? Design decision deferred, but the harness architecture supports either — the agent's token scope is what changes, not the code.
- Access revocation: when an engagement ends, what gets torn down? Repo archive + tenant deactivation + credential rotation. Automate via a closing-ticket template.
- Billing/licensing story: out of scope for this doc.

## 8. What this doc does NOT decide

- **Exact Terraform backend topology** (S3 + DynamoDB vs. Terraform Cloud vs. per-partner isolated). Deferred.
- **Whether pre-prod tests must include a live customer-endpoint round-trip** or if mocked-target-app is sufficient. Likely mocked in pre-prod for hackathon; customer-endpoint round-trip is a Day-6+ upgrade.
- **Promotion SLO** (how fast should pre-prod → prod happen?). Hackathon: whenever the human clicks. Future: auto-promote on green verify + 24h soak.
- **Multi-region prod topology.** Out of scope.

## 9. Hackathon demo vs. Day-11+ vision

| Capability | Hackathon demo | Post-hackathon |
|---|---|---|
| Two-tenant topology | ✅ demo-customer-a-staging + demo-customer-a-prod | Per-engagement tenants |
| `terraform_workspace: staging \| prod` field | ✅ already in template | — |
| Promotion-gate fields in ticket | 🟡 schema added, pipeline writes mocked | Pipeline writes are real |
| Signed Promotion Manifest | 🟡 generated but signature verification is manual | HMAC verify runs as prod-apply precondition |
| Pre-prod verify gate (OIN 12/12) | ✅ replay-test suite green against skeleton today | Live-tenant OIN run added |
| Auto rollback on health-metric regression | ❌ not in hackathon | Day-11+ |
| Partner onboarding | ❌ manual | Tooled in a later sprint |
| Two-of-two promotion signature | 🟡 documented, not enforced | Enforced as GitHub branch-protection rule |

The hackathon demo shows: ticket comes in → agent generates → PR green → Terraform apply to staging → OIN tests run against staging tenant → Promotion Manifest generated → human approves → Terraform apply to prod. End-to-end, one connector, two tenants, signed artifact at the gate. That's the story.
